ในวันที่ 16 มิถุนายน คำสั่งเป็นประโยคเดียว: *“ค้นหาโฟลเดอร์โค้ด claude และรับจาวาสคริปต์ (คอมไพล์ และย่อขนาด) จากที่นั่น … มาดูกันว่าเราสามารถคอมไพล์ได้หรือไม่ :D”* เมื่อมีการคัดค้านอย่างชัดเจนกลับมา — ว่านี่จะโหดร้าย — คำตอบคือวิทยานิพนธ์ที่แท้จริง: *“มันโหดร้าย แต่ยังเป็นการทดสอบความสามารถและขีดจำกัดของเราอย่างแท้จริง ซึ่งก็คือ ทำไมฉันถึงอยากทำ ไม่มีอะไรมาแทนที่แอปในโลกแห่งความเป็นจริงในแง่ของการค้นหาขีดจำกัด”*

หนึ่งเดือนต่อมา ไบนารีที่คอมไพล์แล้วของ Perry ของ Anthropic Claude Code CLI เปิดตัว รัน `/login` ผ่านโฟลว์ OAuth สตรีมการตอบกลับที่แท้จริงจาก API และระบายสีอักขระที่คุณพิมพ์ การไปถึงที่นั่นต้องใช้คำขอดึง **160 คำขอที่รวมเข้ากับ Perry ระหว่างวันที่ 20 มิถุนายนถึง 17 กรกฎาคม** — `MessageChannel` แบบ no-op, อุปสรรคในการเขียน GC บน RegExp ส่วนหัว ซึ่งเป็นคำสั่ง `continue` ที่หมุนเฉพาะบน API จริงเท่านั้น และไม่เคยอยู่บนการเยาะเย้ยของเรา และอีกประมาณร้อยห้าสิบเพิ่มเติม

โพสต์นี้เป็นการทัวร์ชม ไม่ใช่เพราะการคอมไพล์ CLI ของคนอื่นเป็นผลิตภัณฑ์ — เราไม่ปล่อยไบนารี่นี้และจะไม่มีวันทำ — แต่เนื่องจากมันเป็นเครื่องมือในการค้นหาจุดบกพร่องที่มีประสิทธิผลมากที่สุดเพียงเครื่องเดียวที่เราเคยชี้ไปที่ Perry

## จริงๆ แล้ว “การคอมไพล์ Claude Code” หมายถึงอะไร

เป้าหมายการคอมไพล์คือไฟล์ที่กระจายในแพ็คเกจ npm `npm pack @anthropic-ai/claude-code@2.1.112` ให้ `cli.js`: **13 MB ที่ย่อขนาดและดำเนินการเอง JavaScript** ด้วย `#!/usr/bin/env node` shebang. ไม่มีแหล่งที่มา ไม่มีแผนที่แหล่งที่มา ไม่มีขั้นตอนการสร้างของเรา เราชี้ `perry compile` ไปที่ไฟล์นั้น โดยไม่ได้แก้ไข และขอไฟล์ปฏิบัติการแบบเนทีฟ

Perry เคี้ยวมันประมาณ 37 นาทีและสร้าง IR ประมาณ 207 MB ทั่วทั้ง **16,023 ฟังก์ชัน** ซึ่งลิงก์ไปยังไบนารี ~180 MB ฟังก์ชันทุกฟังก์ชันมีชื่อตัวอักษรเดียวและไม่มีคำอธิบายประกอบประเภท และสิ่งทั้งหมดจะต้องทำงานล่วงหน้า — ไม่มี JIT, ไม่มี `eval`, ไม่มีการช่วยเหลือล่ามอย่างขี้เกียจเมื่อคอมไพเลอร์เดาผิด หาก Perry ลดฟังก์ชันใดฟังก์ชันหนึ่งจาก 16,023 ฟังก์ชันเหล่านั้นลงอย่างไม่ถูกต้อง ก็ไม่มีอะไรที่จะตรวจจับได้

ลำดับการให้คะแนนมาจากชุดความเครียดภายในของเรา และเป็นการจงใจไม่ให้อภัย:

```
parse    → perry couldn't even parse it
compile  → parsed, but HIR/codegen errored
link     → codegen ok, but cc/ld failed
run      → linked, but the binary crashed / hung / exited non-zero
ran-ok   → binary exited 0
correct  → output byte-matches node --experimental-strip-types
```

`correct` เป็นเพียงระดับเดียวที่นับ Node v26 คือออราเคิล สิ่งใดก็ตามที่ไม่เหมือนกับไบต์กับการพิมพ์ Node นั้นเป็นข้อบกพร่องของ Perry จนกว่าจะพิสูจน์เป็นอย่างอื่น

## เหตุใดจึงเป็นแอปนี้โดยเฉพาะ

Coding-agent CLI เป็นกอง JavaScript ที่ไม่เป็นมิตรซึ่งต้องคอมไพล์ล่วงหน้า ในไบนารี่เดียวคุณจะได้รับ: React ปรับยอดในเทอร์มินัลผ่าน Ink, เครื่องอ่าน stdin โหมดดิบ, ANSI/emoji-saturated renderer ที่รัน regexes ในทุกเฟรม, การสตรีม SSE ไคลเอ็นต์ HTTP, zod schema ที่สร้างขึ้นเมื่อเริ่มต้น, โฟลว์ OAuth, `worker_threads`, `MessageChannel` ที่ใช้เป็นตัวกำหนดเวลา macrotask WeakMaps ถือสถานะไฟเบอร์, `require` แบบไดนามิก และเลเยอร์ระบบไฟล์ที่เขียนไปยัง stdout ด้วยตัวอธิบายไฟล์

แต่ละระบบเป็นระบบย่อยที่แตกต่างกันของ Perry และแอปจะฝึกระบบย่อยเหล่านี้ *ร่วมกัน* ในวงกว้าง ภายใต้แรงกดดันของ GC ครั้งละนาที ชุดทดสอบของเราเอง — การทดสอบหน่วย Rust 3,000 รายการ, โปรแกรมการถดถอย TypeScript หลายพันรายการ, Node API parity matrix, test262 — ล้วนมุ่งเน้นไปที่การปักหมุดพฤติกรรมที่ทราบ ชุดรวมนี้มุ่งเน้นที่การค้นหาพฤติกรรมที่ไม่มีใครคิดจะปักหมุด

## ข้อบกพร่องของซอฟต์แวร์ห้าประการที่ควรค่าแก่การพูดคุย

### 1. MessageChannel ไม่สุภาพ

`--help` ใช้งานได้ในวันที่ 21 มิถุนายน คำสั่งย่อย *real* ทุกคำสั่ง — `doctor`, `agents`, `mcp list` — หยุดทำงาน ตลอดไป ไม่ยุ่ง: `sample` แสดงกระบวนการที่จอดอยู่ `lsof` ไม่แสดงกระบวนการลูก ไม่มีซ็อกเก็ต มีเพียงสองไพพ์

การใช้งาน `MessageChannel` ของ Perry กำหนดให้ `postMessage` เป็นคำสั่งที่ไม่ทำอะไร และให้ `onmessage` เป็น `null` ดูเหมือนไม่มีปัญหา จนกว่าจะเจอรูปแบบตัวจัดตารางงานของ React ซึ่งใช้ช่องทางข้อความเพื่อจัดตาราง macrotask:

```
const ch = new MessageChannel();
ch.port1.onmessage = flushWork;
ch.port2.postMessage(null);   // schedule the next tick
```

ข้อความถูกทิ้ง การโทรกลับไม่เคยทำงาน และลูปเหตุการณ์ไม่ทำงานบนไปป์ปลุกของตัวเองตลอดไป [#5530](https://github.com/PerryTS/perry/pull/5530) ให้พอร์ตที่มีการจัดส่งเธรดเดียวกันจริง — คู่ที่พันกัน, คิว FIFO, การส่งมอบผ่านแมโครทาสก์ `setImmediate` และงานแมโคร GC เครื่องสแกนรูท ดังนั้นข้อความที่อยู่ในคิวจึงคงอยู่เป็นคอลเล็กชัน

### 2. ตัวเข้าถึงหนึ่งตัวบน Object.prototype มีค่าใช้จ่าย 42 วินาที

ก่อนที่จะแฮงค์ คำสั่งย่อยเดียวกันนั้นเชื่อมโยงกับ CPU เป็นเวลาสิบวินาที การทำโปรไฟล์ชี้ไปที่เส้นทาง `[[Set]]` ทั่วไป และสาเหตุที่แท้จริงคือแฟล็กของกระบวนการทั่วโลก

Perry มีเส้นทางที่รวดเร็วสำหรับการเขียนคุณสมบัติไดนามิก โดยควบคุมไว้ที่ “ปัจจุบัน `Object.prototype` มีตัวอธิบายใดๆ หรือไม่ บันเดิลจะติดตั้งตัวเข้าถึงเพียงตัวเดียวบน `Object.prototype` เมื่อเริ่มต้น ซึ่งพลิกกระบวนการแฟล็กไปทั่วทั้งกระบวนการ และหลังจากนั้น การเขียนไดนามิก *ทุก* ในโปรแกรมก็ใช้การสกัดกั้นอย่างช้าๆ ซึ่งก็คือ O(own-key-count) การสร้างวัตถุที่มีความกว้างกลายเป็นกำลังสอง:

```
20,000-property build, clean process:                 16 ms
20,000-property build, after one Object.prototype accessor:  42,394 ms
```

[#5524](https://github.com/PerryTS/perry/pull/5524) แทนที่ธงสากลด้วยคำถามต่อคีย์ — *`Object.prototype` มีคุณสมบัติของตัวเองสำหรับคีย์ **นี้** หรือไม่* คีย์ที่ขาดหายไปไม่สามารถดักจับได้ ดังนั้นการเขียนจึงปลอดภัยสำหรับเส้นทางด่วน 42 วินาที → 23 ms โดยที่การสกัดกั้นยังคงถูกต้อง

จากนั้น รูปร่างเดียวกันก็ปรากฏขึ้นอีกครั้งสำหรับอินสแตนซ์ของคลาส ซึ่ง Fast Path ไม่รวมอยู่เลย: การสร้าง 20,000 คีย์บนวัตถุธรรมดาใช้เวลา 25 มิลลิวินาที บนอินสแตนซ์ `class` 44 วินาที การแก้ไขสิ่งที่มีความสำคัญอย่างระมัดระวัง การตรวจสอบลูกโซ่ต้นแบบที่ไร้เดียงสาจะข้ามตัวตั้งค่าที่สืบทอดมาและข้อมูลเสียหายโดยไม่โต้ตอบ ดังนั้น [#5528](https://github.com/PerryTS/perry/pull/5528) จะแก้ไขต้นแบบของอินสแตนซ์ผ่านรีจิสทรีของคลาสและเพิ่มดัชนีคีย์กว้าง O(1) ย้อนกลับไปที่ 30 ms และเป็นเส้นตรงอีกครั้ง

### 3. ข้อบกพร่องที่เฉพาะ API จริงเท่านั้นที่สามารถทริกเกอร์ได้

นี่คือสิ่งที่เราบอกผู้คน ภายในต้นเดือนกรกฎาคม ไบนารีที่คอมไพล์แล้วจะดำเนินการ `-p` โดยสมบูรณ์ต่อเซิร์ฟเวอร์จำลองในเครื่องของเรา: เชื่อมต่อ, POST, อ่านสตรีม SSE พิมพ์การตอบกลับ ทางออก 0 เทียบกับ Anthropic API หยุดทำงานถาวรทุกครั้ง

ห่วงโซ่การแก้ไขข้อบกพร่องคือ: การเยาะเย้ยการส่งต่อพร็อกซีพิสูจน์ว่าการตอบสนอง 200 รายการทั้งหมดมาถึงครบถ้วน → การเยาะเย้ยการเล่นซ้ำ ป้อนสตรีมไบต์จริงที่บันทึกไว้ สร้างการแฮงค์ในเครื่องอีกครั้ง → การแบ่งส่วนรายการเหตุการณ์ SSE พบเหตุการณ์ผู้ร้าย → การทำสำเนาสิบบรรทัด

เหตุการณ์ API จริงส่งเฟรม `event: ping` การเยาะเย้ยของเราไม่เคยทำ และ `ping` เป็นเหตุการณ์หนึ่งที่สตรีมลูปของ SDK ข้ามไปโดย `continue` เปล่าๆ Perry ลดระดับ `for await` ลงในไดรเวอร์ที่มีตัววนล่วงหน้าอยู่ที่ *ด้านล่าง* ของเนื้อหาลูป:

```
// what perry emitted
while (!done) {
  ...body...                   // a "continue" here skips the advance…
  result = await it.next();    // …so this never runs. Spin forever.
}

// what it emits now
while (true) {
  result = await it.next();
  if (result.done) break;
  ...body...
}
```

จุดลดระดับหกจุดแยกจากกันมีรูปร่างเหมือนกัน [#6196](https://github.com/PerryTS/perry/pull/6196) ย้ายการเลื่อนไปด้านบนสุดในทุกรายการ บทเรียนที่เราเรียนรู้ซ้ำ: การเยาะเย้ยที่ผ่านไปเป็นหลักฐานเกี่ยวกับการเยาะเย้ย

### 4. regex ที่มีอายุยืนยาวกว่าสตริงรูปแบบของตัวเอง

TUI จะเรนเดอร์ จากนั้นจะตายของ `SIGBUS` ภายในไม่กี่วินาที — เกิดข้อขัดข้อง 12 ครั้งใน 12 ครั้งที่ทำงานภายใต้ชุดควบคุมความเครียดปรับขนาดหน้าต่าง ณ ที่อยู่ที่แตกต่างกันในฟังก์ชันที่แตกต่างกันในแต่ละครั้ง การตรวจสอบเป็นเวลาหลายสัปดาห์ได้ครอบคลุมถึงทฤษฎี GC ที่การทดสอบ A/B ถูกปฏิเสธ ซึ่งรวมถึงหนึ่งใน "การแก้ไข" ของเราเองที่พบว่าไม่มั่นคงและต้องถอนออก

สาเหตุที่แท้จริงคือ Rust สี่บรรทัด `js_regexp_new` จัดสรรส่วนหัว RegExp และจัดเก็บ `pattern` และ `flags` ตัวชี้สตริงที่มีการเขียนแบบ raw — **ไม่มีอุปสรรคในการเขียน** วัตถุรุ่นเก่าชี้ไปที่สายอ่อนสดโดยที่นักสะสมไม่เคยบอกเกี่ยวกับขอบเลย GC รายย่อยกวาดสตริงเหล่านั้นออกจากภายใต้ RegExp แบบสด และการอ่านครั้งถัดไปของช่องที่ว่างเกิดข้อผิดพลาด

เหตุใดจึงปรากฏที่นี่เท่านั้น เนื่องจาก UI เทอร์มินัลมีความอิ่มตัวของ regex — การแยกวิเคราะห์ ANSI และการวัดความกว้างของอีโมจิดำเนินรูปแบบในทุกเฟรม ดังนั้นหน้าต่างระหว่างการจัดสรรและคอลเลกชันจึงถูกข้ามหลายพันครั้งต่อนาที การสร้างซ้ำขั้นต่ำของเรา 6,000 regexes บวกกับปั่นป่วนการจัดสรรโดยเจตนา *ไม่เคย* ทริกเกอร์ มัดกระตุ้นมันทุกครั้ง [#6288](https://github.com/PerryTS/perry/pull/6288) เพิ่มอุปสรรคที่ทั้งสองช่องจำเป็นต้องมีมาโดยตลอด

### 5. อักขระที่คุณพิมพ์อยู่ที่นั่น เฟรมก็โยนมันทิ้งไป

กำแพงที่ดื้อรั้นที่สุด: UI ทั้งหมดทาสีได้อย่างสมบูรณ์แบบ - กล่องต้อนรับ กรอบอินพุต บล็อกเคอร์เซอร์ บรรทัดสถานะ การพิมพ์ `/` จะเปิดเมนูคำสั่ง ดังนั้นการกดแป้นพิมพ์จึงไปถึง React แต่ตัวอักษรไม่เคยปรากฏบนบรรทัดอินพุต

บิลด์ที่ใช้เครื่องมือสร้างแสดงให้เห็นว่า Perry ลงสีอักขระที่พิมพ์อย่างถูกต้องในทุกขั้นตอน จากนั้น `onRender` ขว้าง *หลัง* การทาสี — ลงใน Ink `try/catch` ที่กลืนมันเข้าไป เฟรมถูกละทิ้งก่อนที่จะคอมมิต ดังนั้นทุกๆ การเรนเดอร์ที่ตามมาจึงถูกสร้างขึ้นบนเฟรมว่าง แอปดูแข็งแรงดีโดยไม่สนใจคุณ

มีจุดบกพร่องอิสระสองจุดซ่อนอยู่หลังอาการเดียว:

-   [#6453](https://github.com/PerryTS/perry/pull/6453) — Perry การลด `charAt`/`codePointAt`/`split` เรียกว่า ToString บนตัวรับที่ไม่ใช่สตริงโดยไม่ต้องใช้ตัวป้องกันบังคับ ดังนั้น `undefined.codePointAt(0)` จึงส่งคืน `117` อย่างเงียบๆ — จุดโค้ดของ `"u"` จากสตริง `"undefined"` — แทนที่จะโยน ข้อบกพร่องที่ *ประดิษฐ์* ข้อมูลที่เป็นไปได้นั้นเลวร้ายยิ่งกว่าข้อบกพร่องที่ขัดข้องมาก

-   [#6471](https://github.com/PerryTS/perry/pull/6471) — ตัวบล็อกตัวจริง เมื่ออาร์เรย์เติบโตขึ้น Perry จะทิ้ง stub การส่งต่อถาวรไว้ที่ที่อยู่เดิม การกวาดล้างเล็กน้อยกำลังเรียกคืน stub เหล่านั้นในขณะที่ผู้ปกครองรุ่นเก่ายังคงชี้ไปที่สิ่งหนึ่ง: แคชอักขระของตัวแสดงภาพมีตัวชี้ก่อนการเติบโตบนหน้าเว็บที่ไม่สกปรก การอ่านต้นขั้วเก่าทำให้เกิดความยาวขยะ และทุกเฟรมถูกยกเลิก ตอนนี้ผู้เยาว์จะเก็บต้นขั้วทั้งหมดไว้ ร่องรอยทั้งหมดเรียกคืนโดยเครื่องหมาย


การแก้ไขส่วนที่เปิดเผยในเลเยอร์ที่สาม — วัตถุที่เกิดเป็นสีดำในระหว่างการทำเครื่องหมายแบบเพิ่มจะไม่ถูกติดตาม ดังนั้นทุกสิ่งที่เข้าถึงได้ผ่านวัตถุนั้นเท่านั้นจะถูกกวาดในขณะที่กำลังทำงานอยู่ ([#6494](https://github.com/PerryTS/perry/pull/6494)) และเลย์เอาต์มาสก์ภายใต้ช่องโอเวอร์โฟลว์ที่รายงาน ดังนั้นตัวรวบรวมจึงข้ามไป ([#6506](https://github.com/PerryTS/perry/pull/6506)) ทั้งสองนี้เป็นช่องโหว่ที่ทำให้เกิดความผิดพลาดลึกลับหนึ่งในห้าสิบในโปรแกรมที่คอมไพล์ *ใดๆ* เราคงไม่พบพวกเขาพร้อมกับชุดทดสอบ

## วิธีแก้ไขข้อบกพร่องไบนารีย่อขนาด 13 MB

ไม่สามารถค้นหาสิ่งใดข้างต้นได้โดยการอ่านโค้ด เครื่องมือที่ทำให้ลากได้:

-   **การควบคุมส่วนต่างที่มี Node เป็น oracle** ทุกสมมติฐานจะกลายเป็นโปรแกรม TypeScript ขนาดเล็กที่ทำงานภายใต้ทั้ง `node --experimental-strip-types` และ Perry ไบนารี่ เมื่อเปรียบเทียบแบบไบต์ต่อไบต์ พบข้อบกพร่องในตัวมันเอง นิพจน์คลาสที่ใช้เฉพาะเป็น `instanceof` ทางด้านขวามือเป็นแบบ dead-code-eliminated เนื่องจากการวิเคราะห์ 11 ครั้งไม่สามารถมองเห็นผ่านประเภทโหนดนั้นได้ ([#6245](https://github.com/PerryTS/perry/pull/6245))

-   **เซิร์ฟเวอร์ API จำลองสามเซิร์ฟเวอร์** การจำลองการบันทึก พร็อกซีการส่งต่อที่รวบรวมไบต์การตอบสนองจริง และเซิร์ฟเวอร์เล่นซ้ำที่ฟีดไบต์ที่แน่นอนเหล่านั้นกลับตามที่กำหนด เซิร์ฟเวอร์เล่นซ้ำคือสิ่งที่เปลี่ยน "การหยุดทำงาน" ให้กลายเป็นการทำซ้ำในท้องถิ่น

-   **A PTY ควบคุมการตอบคำถามเทอร์มินัล** เทอร์มินัลหลอกที่โง่เขลาทำให้คุณได้รับ 50 ไบต์และแผงลอย แอปจะตรวจสอบตำแหน่งเคอร์เซอร์ (`ESC[6n`) คุณลักษณะของอุปกรณ์ (`ESC[c`) และสีพื้นหลัง (`OSC 11`) และรอการตอบกลับก่อนที่จะทาสี ตอบคำถามเหล่านี้แล้วคุณจะได้รับหน้าจอต้อนรับขนาด 3,331 ไบต์เต็มรูปแบบ — และการเรนเดอร์ที่เทียบเท่ากับไบต์ระหว่าง Node และ Perry

-   **ลิงก์แมปสำหรับสัญลักษณ์** ไบนารี 180 MB ที่แยกออกมาจะสร้างรายงานข้อขัดข้องที่เต็มไปด้วยออฟเซ็ตดิบ เอาต์พุต `ld64 -map` พร้อมด้วยสคริปต์ที่แบ่งออกเป็นสองส่วนจะเปลี่ยนสิ่งเหล่านั้นกลับเป็นชื่อฟังก์ชัน

-   **A/B ทุกอย่าง** กฎที่เกิดขึ้น ซึ่งเขียนไว้ที่ด้านบนของบันทึกแฮนด์ออฟด้วยตัวพิมพ์ใหญ่: *ไม่เคยสืบทอดทฤษฎี — ทดสอบเลย* สมมติฐานต้นตอสาเหตุสี่ประการติดต่อกันสำหรับข้อบกพร่องหนึ่งข้อได้รับการหักล้างโดยการเรียกใช้ A/B แต่ละรายการ สัญญาณผู้ตรวจสอบสัญญาณหนึ่งที่เราไล่ตามเป็นเวลาหลายวัน (“445 ส่วนที่เก่าหายไป→ขอบที่อายุน้อย”) กลายเป็นสิ่งประดิษฐ์ในการวัด — การตรวจสอบดำเนินการระหว่างการเคลียร์และการกู้คืนชุดที่จดจำ ความคิดเห็นของโค้ดเตือนเกี่ยวกับเรื่องนี้


## จุดยืนที่แท้จริง

จริง ๆ แล้ว: ใช้งานได้แต่ช้า

ใช้งานได้ในปัจจุบัน ไบต์เหมือนกันกับ Node โดยที่เอาต์พุตเทียบเคียงได้: การเริ่มต้น, โหมด `--help`, `--version`, โหมด one-shot `-p` เทียบกับ API รวมถึงการจัดประเภทข้อผิดพลาดและซองจดหมาย JSON, การแสดงผล TUI แบบเต็ม, โฟลว์ OAuth `/login`, การตอบสนองแบบสตรีม และการพิมพ์ นี่คือการวนซ้ำทั้งหมดในเทคเดียว — เปิดตัว `/login` คำถาม คำตอบแบบสตรีม ออก:

สองสิ่งยังคงเปิดอยู่ และอาจเป็นสิ่งเดียวกัน อินพุตจะหยุดการลงทะเบียนหลังจากใช้งานแบบโต้ตอบอย่างต่อเนื่องประมาณหนึ่งนาที ไม่มีข้อขัดข้อง ไม่มีข้อผิดพลาด เพียงแต่หยุดเท่านั้น และ `ESC` จะไม่ขัดจังหวะการตอบสนองบนเครื่องบิน แม้ว่า `Ctrl-C` จะออกจากการทำงานอย่างเรียบร้อย ซึ่งไม่ได้เกิดขึ้นเมื่อสัปดาห์ที่แล้ว (นั่นคือทางออกที่คุณเห็นในตอนท้ายของการบันทึก) เส้นทางออกที่ทำงานในขณะที่เส้นทางขัดจังหวะไม่ได้ชี้ไปที่ผู้ต้องสงสัยรายเดียวกับการเสียชีวิตของอินพุต: เหตุการณ์การกดปุ่มที่หยุดเข้าถึงแอป แทนที่จะเป็นสิ่งผิดปกติกับตัวจัดการของแอปเอง

| รอยเท้าหน่วยความจำ ไม่ได้ใช้งาน| 290 MB แบน| ~420 MB ไต่ระดับ| ~420 MB ไต่ระดับ |

`--version` ตอนนี้ **เต้น Node** และการชนะนั้นน่าอายที่จุดเริ่มต้น: ไฟล์ปฏิบัติการที่คอมไพล์แล้วส่งออกสัญลักษณ์ 300,281 ตัว ดังนั้น ~80% ของการเปิดตัวครั้งนั้นจึง dyld ทำการรวมตัวกันที่มีความละเอียดต่ำ แฟล็กตัวเชื่อมโยงหนึ่งตัวทำการส่งออกเป็น 3 และไบนารีจาก 228 MB เป็น 197 MB ([#6533](https://github.com/PerryTS/perry/pull/6533)) การสร้าง regex ที่ไม่ซ้ำกันแต่ละรายการเพียงครั้งเดียวแทนที่จะเป็นสองครั้ง ([#6534](https://github.com/PerryTS/perry/pull/6534)) และแคชการตรวจสอบการสกัดกั้นต่อร้านค้า ([#6532](https://github.com/PerryTS/perry/pull/6532), [#6541](https://github.com/PerryTS/perry/pull/6541)) รับส่วนที่เหลือไป

บนพื้นที่ 197 MB นั้นก่อนใครจะเป็นผู้นำ: Perry ลิงก์รันไทม์ของตัวเองแบบคงที่และปล่อยรหัสเครื่องสำหรับฟังก์ชันทั้ง 16,023 รายการล่วงหน้าโดยไม่มีอะไรเสียหาย — บันเดิลที่ดำเนินการเองทำให้ทุกสิ่งโดยพื้นฐานแล้วสามารถเข้าถึงได้ ดังนั้นจึงไม่มี DCE แบบข้ามบันเดิล พึ่งพา — ซึ่งหมายความว่า 197 MB เป็นโปรแกรมทั้งหมด *บวก* รันไทม์ในไฟล์เดียว เทียบกับ **138 MB ของไบนารี Node v26 จะชั่งน้ำหนักก่อนที่จะอ่านบรรทัดเดียวของ JavaScript** ของคุณ

แถวการกดแป้นพิมพ์เป็นแถวที่ต้องอ่านอย่างละเอียด เนื่องจากตัวเลข "หลัง" ดูแย่ลง ไม่ใช่: สิ่งเหล่านี้เป็นช่วงของการวิ่งซ้ำๆ และซ้อนทับกัน ดังนั้นค่ามัธยฐานจึงไม่เคลื่อนที่ไปในทิศทางใดทิศทางหนึ่ง นั่นคือความแปรปรวนระหว่างวิ่งต่อรัน ไม่ใช่การถดถอย มันเป็นสิ่งที่เราคาดหวังไว้อย่างแน่นอน การเปลี่ยนแปลงทั้งสามประการเกี่ยวข้องกับขั้นตอนลิงก์ การสร้าง regex และเส้นทาง *ร้านค้า* ค่ามัธยฐานของการกดแป้นพิมพ์ถูกครอบงำโดยเส้นทางคุณสมบัติ *อ่าน* ค่าใช้จ่ายในการรูทต่อการโทร และขั้นตอน GC ของ 40–80 ms ลงจอดภายในหน้าต่างการกดปุ่ม ข้อพิสูจน์เกิดขึ้นในรอบถัดไป: get/set fast lane ทำให้ microbenchmark เข้าถึงภาคสนามเร็วขึ้น 3 เท่า และย้ายตัวเลขนี้ไม่ได้เลย ([#6539](https://github.com/PerryTS/perry/pull/6539)) การชนะด้วย Microbenchmark ที่ไม่แสดงในแอปถือเป็นการวินิจฉัยที่ผิด และเราก็ได้ทำอย่างนั้น

บรรทัดความทรงจำคือแคมเปญปัจจุบัน ตัวรวบรวมการคัดลอกของ Perry *สามารถ* กระชับได้ ปัญหาคือมันมีสิทธิ์ประมาณหนึ่งครั้งต่อ 45 วินาทีของการไม่ได้ใช้งาน ดังนั้นเรือนเพาะชำจะเติบโตใหม่เป็น ~300 MB ระหว่างการเริ่มทำงาน ในขณะที่ Node จะคงที่โดยการกระชับอย่างต่อเนื่อง นั่นเป็นปัญหาเกี่ยวกับความถี่ทริกเกอร์ ไม่ใช่ปัญหาอัลกอริทึม ซึ่งเป็นจุดที่ดีกว่าที่เราเคยเป็นในเดือนมิถุนายนมาก

ไม่มีรายการใดที่จอดอยู่ แคมเปญหน่วยความจำและประสิทธิภาพ *ใช้งานจริง* ในขณะที่โพสต์นี้ได้รับความนิยม — งานทริกเกอร์ GC กำลังดำเนินการอยู่วันนี้ บนไบนารี่นี้ ดังนั้นตารางประสิทธิภาพด้านบนจึงเป็นส่วนหนึ่งของโพสต์นี้ที่เราคาดหวังมากที่สุดว่าจะทำให้เป็นโมฆะ และยิ่งเร็วเท่าไหร่ก็ยิ่งดีเท่านั้น ความถูกต้องใช้เวลาหนึ่งเดือนกว่ากำแพงจะทะลุผ่านได้ สิ่งที่เหลืออยู่คือปัญหาความถี่ทริกเกอร์และปัญหาเส้นทางการอ่าน ซึ่งทั้งคู่เข้าใจดีแล้ว ทั้งคู่กำลังดำเนินการอยู่ เราคาดหวังว่าสิ่งนี้จะรู้สึกราบรื่นมากกว่าแค่ถูกต้อง และเราคาดว่าจะเกิดขึ้นเร็วๆ นี้

## ทำไมเราจึงทำเช่นนี้

ไม่มีการแก้ไข 160 รายการที่เกี่ยวข้องกับ Claude Code อุปสรรคในการเขียนที่หายไปบนส่วนหัว RegExp ทำให้หน่วยความจำเสียหายในโปรแกรม *ใดๆ* ที่สร้าง regexes ภายใต้การโหลด `for await` โดยมี `continue` ในสตรีมคอนซูเมอร์ใดๆ ข้อความที่ปล่อย `MessageChannel` จะทำลายแอปที่มีรูปทรงตามกำหนดเวลาของ React แฟล็กตัวอธิบาย `Object.prototype` ทำให้โปรแกรม *ทุก* ที่สัมผัส `Object.prototype` อยู่ในวัตถุกำลังสองในวัตถุที่กว้างที่สุด

ข้อบกพร่องเหล่านี้ทั้งหมดอยู่ใน Perry ในขณะที่ CI ยังเป็นสีเขียว ในขณะที่ตัวเลข test262 เพิ่มขึ้น ในขณะที่เมทริกซ์พาริตี้ Node กล่าวว่า 97% JavaScript ของบุคคลอื่นใช้เวลาถึง 13 เมกะไบต์ ในการทำงานจริงกับ API จริงในเทอร์มินัลจริง เพื่อคลายการทำงาน

มีอีกสิ่งหนึ่งและเป็นส่วนหนึ่งที่เราพบว่าสนุกที่สุด Perry ไม่ได้เขียนด้วยมือเพียงลำพัง งานส่วนใหญ่รวมถึงแคมเปญ *นี้* จำนวนมากที่เขียนด้วย Claude Code เซิร์ฟเวอร์จำลอง, การควบคุม PTY, ตัวรันดิฟเฟอเรนเชียล, ค่ำคืนอันยาวนานของการแบ่งส่วนข้อผิดพลาด GC ตอนสี่โมงเช้า: เซสชันของตัวแทน ตรวจสอบและรวมเข้าด้วยกันโดยมนุษย์ ไม่ใช่ Perry ทั้งหมด และไม่มีการโต้แย้งมากนัก แต่พอทำให้ประโยคนั้นเป็นจริงทั้งสองทาง

คอมไพเลอร์ที่ใช้ Claude Code เป็นส่วนสำคัญที่สร้างโดย Claude Code
